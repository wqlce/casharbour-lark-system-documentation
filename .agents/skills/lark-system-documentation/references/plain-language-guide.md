# 业务可读性与去技术化写作规范

适用于所有面向业务、产品、教务、运营及接手同事阅读的**产品文档**、**正式服更新日志**和**测试服更新日志**。本规范用于解决文档中常见的“工程黑话过多、免责声明冗长、信息表头太重、用户抓不住重点”问题。

## 1. 读者定位与“前轻后重”原则

- **产品文档**：主读者是产品、教务、运营及接手系统的同事。重点讲清“解决什么问题、谁在什么场景下怎么用、有哪些规则和边界、还缺什么待确认”。
- **正式服更新日志**：主读者是非研发的业务使用方。重点讲清“谁获得了什么新变化/解决了什么痛点、入口在哪、使用要注意什么、目前能用多少”。
- **测试服更新日志**：主读者是上手体验并验收的业务/产品/测试同事。上半块必须直接给出“测试入口、前置条件、操作步骤、预期结果与已知限制”；研发部署与测试计数作为下半块备注或链接至技术文档。

**核心原则——前轻后重**：
前台只保留业务读者关心的内容；文档编号、修订号、产品版本、Git 分支、commit、标签、SemVer 补登记说明、单测通过数、部署回读验证等**工程与审计信息**，统一沉底到文末《归档与追溯信息》《维护说明》或关联技术文档，绝不阻塞开头第一屏，也不插进每条功能说明中间。

## 2. 结构分层标准

### 2.1 产品文档结构
1. **顶部《基本信息》**（仅 4 行）：
   - `适用系统与端`
   - `当前可用状态`（用简短正面标签，如：`已正式上线（部分筛选待验收）` / `仅测试服可用` / `未开发`）
   - `负责人`
   - `最后更新`
2. **业务摘要**（1~2 句话）：说明核心能力、适用对象与最需要关注的范围。
3. **正文**：按实际功能、用户任务或业务场景展开。
4. **文末《归档与追溯信息》**（二列表）：集中放置 `需求名称`、`文档编号 / 文档修订`、`文档状态`、`交付状态`、`产品版本`、`当前分支 / 发布标签（适用时）`、`证据日期`、`关联资料`。

### 2.2 正式服更新日志结构
1. **顶部《基本信息》**（仅 4~5 行）：`项目 / 子项目`、`环境`（附测试服日志链接）、`适用用户与端`、`维护人`、`最后复核`。
2. **更新条目**（按实际正式发布日期倒序）：
   - **日期标题**：`YYYY-MM-DD｜一句话主题`
   - **元信息一行**：`**适用：** xxx ｜ **状态：** 已上线（必要时附带括号内的简短边界，如：已上线（微信跳转待确认））`
   - **编号功能点（从 1 开始）**：每条严格控制在 **2~3 句业务人话**，标题使用用户视角；必要时在条目下缩进列出 `使用入口`、`注意事项`、`当前限制`；最后附来源/关联链接。
   - 不在条目开头贴版本号吐槽、SemVer 缺失说明或补登记声明。
3. **文末《维护说明》**：统一收拢历史梳理依据、版本补登记说明、待验收跟踪汇总。

### 2.3 测试服更新日志结构
1. **顶部《基本信息》**（同正式服，附正式服日志链接）。
2. **每条测试交付拆为上下两块**：
   - **上半块（给业务验收看）**：
     - 一行状态：`适用对象 ｜ 测试状态 / 正式状态（如：测试服已部署，待业务验收 ｜ 未上正式服 或 已上线正式服 YYYY-MM-DD）`
     - `测试入口与账号前提`（网址、权限或白名单要求）
     - `操作与验收步骤` + `预期结果与已知限制`（表格或序号步骤，讲清怎么点、看到什么算过、已知有哪些限制）
   - **下半块（研发备注）**：
     - 收拢测试部署批次、源码与制品版本说明、自动化测试覆盖情况、白名单/临时数据清理情况，以及关联技术/发布证据链接。

## 3. 正文禁词与“人话翻译”红线

以下内容**严禁出现在产品文档和正式服更新日志的用户正文中**（测试服更新日志也应将其隔离在下半块“研发备注”或技术文档中）：

| 禁止出现在用户正文的词汇/表达 | 正确处理方式（移到哪里 / 怎么改写） |
|---|---|
| `SemVer`、统一发布号、源码补登记、运行制品构建、构建时版本、版本治理待补 | 正文**直接删除**；确需记录时放文末《归档与追溯信息》《维护说明》或技术文档 |
| `main`、`feat/*`、发布分支、`commit`、发行标签、JS/CSS 回读、制品回读 | 正文**直接删除**；仅保留在文末归档表或关联技术文档 |
| `隔离数据库回归`、`470项通过447项`、单元测试、健康检查、匿名访问保护、合成记录 | 正式日志**删除**；测试日志放研发备注；必要时在测试区用一句业务话代替（如“研发已完成基础功能与数据核对，待业务实操确认”） |
| 真实表名、字段名、SQL、接口路径/参数、`Unicode字符`、微信模板 ID、底层字段键名（`thing5`/`const4`/`time20`） | 移入 `02｜开发文档` 或 `03｜数据、接口与配置`；业务文档只写“最多显示约 20 个字”“通知卡片显示课程名称和截止时间” |
| `异步`、`定时调度`/`定时器`、`幂等`、`回滚`、`并发发送`、`发现窗口` | 翻译为可感知的业务规则（如“提交后通常几分钟内同步”“截止前约 48/24/4 小时各提醒一次，不会重复发”“若错过提醒时间点不再补发”） |
| 大段防御性免责套话（“不能由文档有效推定已上线”“本条补登记不代表再次部署”“该确认仅针对 X 不代表全部场景验收”“不拿当前值冒充历史值”） | **全部替换为简短正面标签**，例如：`已上线`、`已上线（筛选与导出待复核）`、`仅测试服，未上正式服`、`详情链接跳转待最终确认`；补登记说明统一放文末《维护说明》 |

## 4. 写作预算与改写对照示例

- **正式服标题**：用“用户获得了什么变化”代替“研发做了什么优化”。
  - 避免：`观看时长统计列表查询优化` → 改为：`观看时长统计打开速度变快`
  - 避免：`课程到点自动更新状态与入场按钮` → 改为：`上课时间一到自动亮起“进入直播”按钮`
- **篇幅预算**：正式服每条功能描述不超过 **2~3 句话**，不把背景、原理、限制全部堆成一大段文字。

### 对照示例 1：正式服更新日志（查询优化）
- **原写法**：
  > 产品版本：源码版本事后补登记为 1.0.1；本次登记未重新部署，实际运行制品构建时版本为 1.0.0。
  > 1. 观看时长统计列表查询优化：进入“师资统计 → 观看时长统计”后，继续按原有条件查看观看时长与单元完成度。用户确认正式服首页列表正常且明显变快。注意事项：筛选、学校权限和现有汇总导出尚待单独业务验收；观看数据按现有同步周期更新。
- **改写后**：
  > **适用：** 教务及后台管理人员（管理端） ｜ **状态：** 已上线（筛选与导出待业务复核）
  > 1. **“观看时长统计”打开明显变快**：进入“师资统计 → 观看时长统计”，页面加载速度大幅提升；原有的查询、翻页和汇总导出操作保持不变。
  >    - **注意事项：** 观看数据按现有周期同步，当天新观看不一定实时刷新；本次未新增单个单元明细导出。

### 对照示例 2：正式服更新日志（作业提醒）
- **原写法**：
  > 本次后端未建立统一 SemVer 发布号，版本治理待补……系统仅向尚未提交的有效正式选课学生自动发送；超过提醒发现窗口不补发历史节点……长标题最多 20 个 Unicode 字符……该确认针对卡片收件和展示，微信端最终放行仍待确认。
- **改写后**：
  > **适用：** 国际课正式选课学生（微信公众号通知、学生端作业页） ｜ **状态：** 已上线（微信点击跳转待最终确认）
  > 1. **未交作业在截止前自动发微信提醒**：单元作业和课程大作业在截止前 48、24、4 小时，会自动给还没交作业的学生发微信通知（同一截止时间每个节点只发一次）。
  >    - **注意事项：** 需已绑定并关注公众号才能收到；已交作业或人工补录成绩的不会收到催交；调整截止时间后会按新时间提醒，已错过的时间点不再补发。
  >    - **当前限制：** 目前已有老师确认可正常收到提醒卡片，从微信卡片点进官网作业页的跳转放行还在最终确认中。

### 对照示例 3：产品文档（通知规则）
- **原写法**：
  > 模板：KDpM7w4gGAqFKMarnlkDvBTxCxYizGtFkxL6nSS17Uo。字段为 thing5 姓名、thing1 课程名称、time20 报名时间。
- **改写后**：
  > 报名成功后立即发送微信服务号通知，卡片上展示：**学生姓名**、**报名项目/课程名称**、**报名时间**。（模板编号与字段映射见关联技术文档）

### 对照示例 4：测试服更新日志（上下分块）
- **原写法**：
  > 两套后端已分别部署，测试环境限制为单个验收学生白名单……两套测试构建合计470项：447项实际通过、23项跳过，其中新增提醒34项全部实际通过……隔离数据库回归已覆盖。
- **改写后**：
  > 上半块（给业务验收看）只写：测试页链接、需用白名单内已关注公众号的测试账号、操作 1-2-3 步、预期在什么时候看到什么卡片文字、目前哪些条件受限。
  > 下半块（研发备注）再写：两套后端测试部署批次、白名单限制说明、自动化回归 34 项新增用例通过及测试后临时数据已清理。

## 5. 两阶段写作法与写入前 4 项可读性自检

AI 在面对代码 diff 和部署日志时，极易把工程细节直接带入用户文档。执行文档任务时必须拆成两步：

1. **第一阶段（技术与审计落盘）**：先把版本号、SemVer 变更级别、分支、commit、标签、测试通过数、部署回读结果等全部写入 `02｜开发文档` / 发布证据文档（或目标文档文末的归档区）。
2. **第二阶段（切换“业务编辑视角”写正文）**：合上代码细节，只站在教务、运营、产品或终端用户的视角撰写产品文档与更新日志。

写入或更新飞书文档前，必须逐项通过以下 **4 项可读性自检**：
1. **10 秒首屏原则**：第一屏能否在 10 秒内看懂“给谁用、改了什么、现在能不能用”？没有被 10 行重型表格或长免责声明挡住？
2. **零黑话检查**：产品文档正文和正式服更新日志中，是否已清零代码/Git/版本治理/测试计数/底层键名词汇？
3. **正面标签检查**：状态和未验收边界是否已压缩成简短正面标签，没有大段“不代表/不等同/不冒充”式的防御性套话？
4. **外行可读检查**：把正文直接发给一位不懂技术的教务或运营同事，Ta 能否无需再找研发解释就能看懂规则或照着验收？
