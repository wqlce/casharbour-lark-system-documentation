# 更新日志默认写法

适用于本Skill后续编写或修订的更新日志。沿用用户在教师发展服务任务中确认的组织方式，不照搬该项目的编号、日期、版本、扫描计数或业务结论。各系统事实、编号、权限与归档要求仍从实时飞书治理和项目记录核实；仅调整写法不会授权发布、重打标签或批量重写历史文档。

## 默认结构

### 文档信息

放在标题之后、正文之前，用“项目｜内容”二列表格。按实时治理的必填项填写，并将文档编号、文档修订、产品版本、系统与子项目、具体端/服务、状态、上线日期、负责人、最后复核等分别列清；适用时补分支、标签和基线登记日期。不要把字段挤成一条长句，也不要放到文末。

产品版本、文档修订和记录编号是不同对象。上线日期与事后版本登记日期分开。负责人默认由每次执行时的`lark-cli auth status --json --verify`读取已验证user姓名，不留空或写“待指定”，不照抄上一次账号；用户另有明确指定时采用指定人，身份无法核实时先解决身份问题。提交和制品摘要等细节集中到内部技术记录，正文用链接追溯。

### 原始需求与本次范围

用短段落说明最初要解决什么问题、本次实际发布了什么、涉及哪些端和用户。分阶段实施的需求，交代本次增量与前次发布的关系；只有在编写基线或完整阶段汇总时，才概述此前各阶段，保留真实发布日期，避免每条日常更新都堆满历史。

安全整改、身份迁移或权限改造要交代完整目标与实际范围，不只列后续可见的兼容Bug。有现成复核记录时，标出复核日期、已修与残留、延期决定，并链接逐项证据；没有新复核，不把历史计数写成当前新扫描结果。普通更新不强加安全审计章节。

### 本次变化

按功能或问题组织，使用“原问题｜上线后的变化”表格或简短并列项，让非开发读者看懂使用结果。仅记录有依据的变更，不把构建步骤、排障过程或计划中的功能写成已上线成果。用户数据、凭证与内部地址不进入业务正文。

### 验收结果与待办

先核对已有用户确认、测试、部署和运行回读，再按功能列“场景｜当前结果｜下一步”；环境、日期和来源可按需要独立列出。

- 已上线：有对应正式部署和版本依据。
- 已验收：有明确场景和结果，说明真人业务、页面核对或自动化回归的范围。
- 待验收：指定场景仍缺结果；列具体补测动作与责任角色。
- 待确认：尚需业务或产品决定的规则。
- 未纳入本次：单独跟踪，不混写成已发布修复。

发布与验收分开表达。保留已有通过结论，剩余事项逐项列出；不能用一个总状态覆盖所有功能。开放事项集中写一次，不反复堆叠“不能证明、尚未闭环”等限定语；已经上线但缺业务回执的事项不能标成已验收或问题已关闭。

### 注意事项与回退

保留影响实际使用的限制及简要回退说明，详细操作、备份、哈希和日志链接到内部技术记录。没有精确回退点或未演练时如实标注，不补写为已完成。

### 关联资料

链接必要的产品、技术、上一版本及未关闭问题，避免反复插入相同链接或链接自身。已有页面原地修订，完成后回读正文、状态、链接和栏目。

## 表达与使用边界

简单更新可以合并相邻章节，保留开头信息表和关键事实；不要为了模板制造无内容章节。正文用业务语言，技术证据分层保留。文档本身应便于非开发读者阅读，不默认额外生成独立对外稿，不改变知识库分享权限或代为外发。

实际填写时读取知识库中的《更新日志通用模板（业务版）》；入口见knowledge-base.md。业务页无需列出命令、Git哈希或服务器信息，这些字段在关联技术记录中满足追溯即可。
