# 更新日志写法与维护

适用于各项目更新记录。每个项目按环境维护两份独立固定文档：“项目｜正式服更新日志”和“项目｜测试服更新日志”。不能只在同一篇内增加测试章节。完整模板以飞书《更新日志通用模板（业务版）》为准；本文件保存维护规则，不缓存模板正文或项目发布事实。

## 定位对应项目文档

- 先读[项目更新文档登记](project-release-pages.md)，按主系统、子项目和环境匹配；同属一个系统或项目不代表应写入同一篇。
- 使用登记的 Wiki URL 读取正文和节点信息，核对项目、环境、标题、对象及栏目。匹配正确后直接更新该环境固定文档，不因日期、年份或版本变化另建。原有未注明环境的固定页保留链接作为正式服页，新增独立测试服页并互链；同环境有既有页面时优先复用。已确认的绑定不需要重复请用户确认。
- 多个候选、归属冲突或已登记页面失效时，先核实目录及相关说明；无法唯一定位才询问，不猜链接、不静默改绑或新建替代页。
- 首次建立关系时列出“项目 → 文档名称 → 放置栏目”。用户要求先确认的，在确认前不创建项目文档、不把候选登记为生效绑定；确认后创建、回读，再登记真实 Wiki URL、docx token、父节点与确认日期。
- 已有单次发布记录保留为来源，不批量删除、改名或搬迁。独立发布证据记录仍使用实时治理要求的 REL 编号；固定汇总页不新增一次发布编号。只有建立新项目入口时创建一次，日常更新维护原页面。

## 环境、部署与正式上线状态

- 正式服日志只收录有正式发布依据的功能及该发布的限制、验收待办。测试服功能、未部署计划和发布状态不明的事项不得混入正式页维护说明。
- 测试服日志按实际测试部署日期倒序，只将已确认测试部署的功能列入更新时间线。待部署或来源矛盾的材料可在该页单列“待发布/待核实资料”，明确尚不能认定测试服可用，保留原日期与来源；空页面如实写尚无可确认的测试部署记录，不推断项目从未更新。
- 每项测试交付分别记录测试部署状态、验收状态、正式发布状态。“已上线”在测试页专指已正式发布，不能用它表示仅测试服部署成功。
- 取得同一功能、端和范围的正式发布依据后，在原测试条目注明“已上线（正式服）”、实际正式发布日期和正式日志链接，同时更新正式服页；原测试日期与历史验收结果保留。确定未正式发布的写“未上线（正式服）”；证据不足的写“正式发布待核实”，不得勾选或标记“已上线”。
- 部分前端/后端或功能发布时分项标记，不能整批宣称已上线。正式发布不等于业务验收通过；正式回滚或撤回后记录当前状态和日期，保留此前发布事实。

## 文档信息与时间线

文档标题及章节标题直接说重点，不用疑问句。正文先放“文档信息”标题及二列信息表，说明项目/子项目、环境、适用用户与端、文档状态、维护人、文档修订、最后复核及另一环境日志链接；摘要在信息表之后。

每份日志按自身环境的实际部署日期倒序排列，可按年份分组；日期下可写真实产品版本、简短主题和适用对象。没有统一产品版本就如实说明，不能把文档 V1.0 当作软件版本。测试部署日期、正式上线日期、补登记日期和文档修改日期分别记录；日期未核实就标明，不用编辑日冒充部署日，也不因正式上线而重排或覆盖原测试日期。

## 测试服写法

测试页供教务、产品、测试与发布维护者理解并实际验证功能，细致程度高于正式服短公告。按用户任务和业务分支讲清入口与权限前提、准备材料、操作顺序、条件与结果、异常如何处理、覆盖或删除影响；有意义的条件比较用表格，连续操作用步骤，不机械复制固定章节。

每项给可执行的验收场景与预期结果，区分已验证、待验证和已知限制，关联产品规则与技术证据。文件导入等会改业务记录的操作，明确成功人数口径、失败是否写入、重试前置及清空/覆盖行为。测试日志不能因写得更细而变成源码或部署命令清单，也不得将尚未实现的设想写成测试服现有功能。

在对应时间位置插入历史补登记，不把它当新发布置顶。相同发布先合并已有条目；发布日期相同但独立发布的，按有依据的版本或主题区分。时间线无已确认上线记录时如实写明，不能编造历史或把计划列入已发布内容。

负责人默认取执行时已验证的飞书 CLI user 姓名，用户明确指定时按指定填写。只有用户明确要求变更负责人时才替换已有业务责任人的记录；文档维护人与业务确认人分开。

## 功能点与注意事项

- 每次更新按实际功能编号为 1、2、3……，从 1 重新开始；同一功能的入口、规则、限制、注意事项不能各占一个同级功能编号。
- 编号后的短标题直接说明用户获得的功能或变化，再用短句说明使用结果。必要时在功能下用缩进项目符号标注“使用入口”“注意事项”“当前限制”等；没有这些信息就省略，不填“无”或强凑模块。
- 注意事项紧邻它所属的功能。适用对象、来源链接不伪装成功能点；多个独立功能即使共用一个日期，也分别编号。
- 保留真正影响使用的条件、权限、默认值、范围和未支持能力；不能为了精简把部分可用写成全部可用。正文使用业务语言，术语必要时就地解释。
- 背景只在有助于理解变化时简短交代，不强制每次重写“背景、范围、验收、回退”一整套章节。

## 发布事实、验收与内部记录

先核对原需求、正式部署、已有业务确认和验证记录。已上线、已验收、待验收、待确认、未纳入本次分别表达；已有通过结论不能被另一项未完成验收覆盖，也不能把上线等同于全部验收通过。

用户必须知道的功能限制留在对应功能下。截图核对过程、详细测试、验收待办、发布分支、提交、制品、恢复步骤等写入文末维护说明或关联技术/发布记录，不作为面向用户的同级功能点。验收缺口影响实际使用时，用户正文同时保留简短限制，不以移入内部记录掩盖风险。

安全整改、身份迁移等专项的完整范围、带日期的历史复核结论及剩余事项继续在内部证据中保留，不拿后续兼容修复替代整个专项，也不把历史统计当作当前核查结果。计划、仅测试服、纯内部维护不能包装成正式用户已获得的新功能；测试服实际部署的变化应写入测试日志。

## 飞书通知

需要通知时，从同一条更新提炼短文案，保留功能编号、必要入口、对应注意事项，并链接到固定时间线的对应条目。验证过的现有 block ID 才能用于锚点；修改后若 ID 改变，应更新相关详情链接。

生成或修订文档不等于获准发送。实际发送须有用户明确授权及明确受众；按需要核实详情链接的访问范围。补历史、改错字或补验收证据不自动群发。发送后记录发布条目、接收对象、发送时间及结果，避免重复通知。未经授权不改分享权限，不配置自动发送。

## 完成核对

回读全文或修改范围，确认项目与环境绑定正确、两环境互链、文档信息最前、自身环境日期顺序正确、功能编号连续、注意事项位于所属功能下、没有重复或丢失边界。测试页的每项“已上线”核对正式发布范围、日期与证据；无依据不得标记。迁移混合内容时先保存快照并回读目标，再定向移除源页对应块，保留未迁移的历史及来源。没有完成回读，不声称更新成功。
