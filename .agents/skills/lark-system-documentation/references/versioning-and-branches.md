# 版本与分支治理

适用于涉及代码、接口、数据协议、发布、回滚或更新日志的系统文档任务。版本语义以知识库《版本控制指南》为准；本文件只规定归档时必须核实和记录的项目级信息。

## 先核实事实源，再自动维护

1. 先在项目根目录读取版本事实源：`package.json`、`pyproject.toml`、`pom.xml`、`VERSION`、`gradle.properties`、`Cargo.toml` 或项目明确指定的等效清单。不得从 README、飞书正文或代码常量猜测版本；多个清单的值不一致时，先报告冲突，不自行选一个覆盖。
2. 核实 `git branch --show-current`、`git rev-parse --short HEAD`、现有标签和 `CHANGELOG`。没有本地仓库、版本源或访问权限时，记录“未建立/待核实”，并说明缺口。
3. 用户于2026-10-25明确授权所有项目按同一规则自动新增和调整版本。在已获授权的开发/发布任务中，按实际变更计算SemVer并更新唯一版本源、lock/相关清单与`CHANGELOG`，无需逐次确认版本号；兼容修复升patch，新功能/弃用升minor，不兼容公共接口或数据协议升major，同批按最高级别处理。0.y.z及预发布沿用实时《版本控制指南》的阶段规则。
4. 版本准备须幂等，纯文档/测试/构建维护、只改版本字段的登记提交或重复构建不虚增产品版本。将实际版本、分支、commit、标签及部署回读写入对应文档。版本自动维护不等于自动部署，也不授予默认分支推送、业务数据或权限变更。

## 尚无版本号的项目

按已核实的项目阶段与现行版本控制指南建立基线，不因缺少单次版本确认而暂停已授权工作。多个有效版本源冲突、真实运行提交不明或发布归属无法确定时先核查，不编造历史版本。基线登记须同时写入唯一版本源、`CHANGELOG`和系统总览或技术文档；未落地的部分如实记录。

| 项目状态 | 初始版本 | 说明 |
|---|---|---|
| 新项目或尚未对外稳定承诺的存量项目 | `0.1.0` | `0.y.z` 表示初始开发阶段，允许快速迭代。 |
| 已在生产运行、已有稳定 API 或被其他项目依赖 | `1.0.0` | 按已核实的现有版本或稳定运行基线登记，不因已生产就覆盖现存版本号。 |
| 只有文档整理、没有代码或可发布制品变更 | 不发项目版本 | 仅提高文档版本或复核日期。 |

交付时说明版本来源或缺口、变更级别、实际`X.Y.Z`、预发布阶段、标签指向及构建/部署证据。现有版本不因文档补登记而追溯改写；各项目沿用各自真实基线，不强制改成同一个数字。

## SemVer 递增

标准格式为 `X.Y.Z`，各段均为无前导零的非负整数：不兼容的公共 API 或数据协议改动升主版本，兼容的新功能或弃用声明升次版本，兼容 bug 修复升修订号。预发布使用 `-alpha.N`、`-beta.N`、`-rc.N`；构建信息可追加 `+`，但不参与版本排序。已发布版本不可改写，改动必须形成新版本和新标签。

## 分支命名

分支名使用小写 ASCII、短横线分词；主题要能从名称直接识别，不使用个人名、日期或含糊的 `test`、`fix`、`new`。有需求/缺陷编号时置于主题最前。

| 类型 | 格式 | 示例 | 使用边界 |
|---|---|---|---|
| 稳定线 | `main` | `main` | 只接收已验收的合并，不直接开发。 |
| 日常集成 | `develop` | `develop` | 项目采用时承接集成版本；没有该分支不强建。 |
| 功能 | `feature/<ticket>-<topic>` | `feature/CRM-184-order-export` | 单一可交付功能。 |
| 修复 | `fix/<ticket>-<topic>` | `fix/CRM-219-callback-retry` | 已知缺陷的兼容修复。 |
| 紧急修复 | `hotfix/<ticket>-<topic>` | `hotfix/CRM-231-login-outage` | 生产故障优先修复，合并后补齐正常分支。 |
| 发布收敛 | `release/X.Y` | `release/1.4` | 上线前冻结范围，只处理发布阻断问题并产出 `rc`。 |
| 维护线 | `support/X.Y` | `support/1.3` | 仅在需要持续维护旧主次版本时使用。 |

分支名中的 `<ticket>-` 在没有编号体系时省略，例如 `feature/order-export`。名称改变、跨系统改动或数据协议变更不应继续复用旧功能分支；新建分支并在技术设计中链接关联记录。

## Codeup Git 标签

Codeup 的代码库使用标准 Git 远端时，可以直接推送 Git 标签；无需为每个版本单独创建分支。标签是不可变的发布锚点，不替代唯一版本源、`CHANGELOG` 或发布验证。

1. 按当前任务交付范围和统一授权确定目标版本及提交，先核实该commit位于`main`或对应`release/X.Y`发布线；版本号与标签常规维护无需重复询问。
2. 在该 commit 创建带中文说明的标签：`git tag -a vX.Y.Z -m "发布版本 X.Y.Z" <commit>`，再执行 `git push <remote> vX.Y.Z`。
3. 用 `git ls-remote --tags <remote> refs/tags/vX.Y.Z` 回读远端标签，并将标签、commit、分支和验证结果写入更新日志。

不要在未确认的 `feature/*` 分支上打正式标签；需要联调时按实际阶段创建 `vX.Y.Z-alpha.N`、`vX.Y.Z-beta.N` 或 `vX.Y.Z-rc.N`。已推送的版本标签不得重打或移动，发现错误时发布新版本标签。

## 发布与归档最小证据

规范发布记录应具备：`上一版本 -> 本版本`、变更级别（major/minor/patch）、唯一版本源位置、标签、发布分支、commit、`CHANGELOG` 条目、验证结果和回滚点。预发布必须标明环境与阶段。只有代码、构建或测试环境证据不能写正式“已上线”；存量项目已有可核实正式部署证据但缺少统一版本、标签或CHANGELOG时，如实写“已正式发布；版本治理待补”，登记已有制品、日期和恢复依据，不因缺标签篡改部署事实，也不伪造版本信息。

业务版更新日志的正文保留产品版本、真实发布状态、日期和分项验收；分支、commit、标签及回滚操作等技术证据可放在其链接的技术记录中，无需在业务页重复展开。存量版本事后补登记时，如实区分原上线日期与版本登记日期，不把已核实的历史上线写成重新发布。

正式服和测试服各维护独立日志及发布日期。测试条目只有在对应范围正式发布已核实后才标“已上线（正式服）”，附正式发布日期与日志链接；测试部署成功、测试通过或准备发布均不满足该标记条件。正式上线与业务验收分别记录，部分端上线只标记实际发布部分。

## 自动流程与运行版本核验

各项目优先复用其技术栈已有发布工具；新项目首次纳入管理时即接入版本准备、正式发布校验和构建清单，不再延至后续维护。存量项目的接入范围、提交分支、远端回读及未合入主线状态，须以实际接入记录核实，不能把统一规则或分支接入写成已部署。准备环节按上次发布锚点收敛本端变更，构建环节读取已提交版本并产出版本、完整commit、环境与构建时间，发布后回读实际制品及其入口。前端可生成`version.json`，后端使用已有版本接口或构建信息；不强制不同技术栈复制同一脚本。

国际课学生PC已在2026-10-25接入`npm run release:prepare`、`release:check`与构建`version.json`，首次纳入自动治理的正式版本2.0.1。此为已核实示例，不作为其他项目的版本或上线事实。纯构建重跑不改变版本源；有待发布业务变更却未登记版本时，正式发布校验应阻止沿用旧号。
