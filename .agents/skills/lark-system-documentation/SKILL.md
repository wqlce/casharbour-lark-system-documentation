# 系统文档归档

将一次需求、改动或异常沉淀到飞书知识库中正确的系统和栏目。完成标准是“文档已按现行规则归档并回读验证”，不是只生成一段正文。

## 先读的规则

1. 先阅读 [知识库配置](references/knowledge-base.md)，确认目标空间和治理文档链接。
2. 涉及代码改动、发布、更新日志或交付版本时，再阅读 [版本与分支治理](references/versioning-and-branches.md)。飞书中的《版本控制指南》是版本语义的当前权威；本参考将其转为本 Skill 的项目归档动作。
3. 按当前环境的 `lark-doc`、`lark-wiki`、`lark-shared` Skill 执行。文档内容读写必须使用 `--as user`。
4. 每次任务先从知识库读取有效的《知识库文档编写与维护规则》、产品模板、技术模板；涉及更新日志时还须读取《更新日志通用模板（业务版）》。它们是当前标准，本Skill通过引用使用，不另存一套会漂移的飞书模板正文。
5. 写入、创建、移动前确认用户的任务已授权这些写操作。删除、覆盖既有正式文档、移动历史资料或改变权限时必须单独取得明确授权。

## 任务输入与定位

先从用户材料中提取：系统、功能或事项、目标读者、文档类型、当前状态、负责人、文档版本、项目发布版本、当前分支、关联资料和是否已经上线。

若关键信息未提供：

- 系统不明确时，先在目标 Wiki 的一级目录中检索，无法可靠归属才询问。
- 文档负责人默认取执行时已验证的飞书CLI登录用户。按lark-shared身份参考运行`lark-cli auth status --json --verify`，核实user身份、账号有效性及姓名后填写；不留空、不写“待指定”，不以本机名、GitHub账号或bot名称代替。用户另有明确指定时采用指定人；无法核实身份时先解决身份问题，不猜姓名，也不额外申请与取负责人无关的通讯录权限。
- 其他非阻塞字段（如未知文档修订或发布日期）如实注明待确认。项目发布版本与当前分支适用时必须按版本与分支治理规则从代码事实源核实；未建立版本体系的项目按现行版本指南和已核实阶段建立基线；所有项目已获2026-10-25统一自动版本维护授权，具体见版本与分支治理参考。不能把 `[待确认]` 当作永久替代，也不能编造运行版本。
- 有已有草案、旧文档或链接时，先读原文和对应系统目录，避免重复创建。

将文档归入下列标准栏目；实际 node token 必须每次从 Wiki 实时查询，不能只依赖本地记忆：

| 文档类型 | 标准栏目 |
|---|---|
| 系统定义、边界、关键入口 | `00｜系统总览` |
| 正式 PRD、业务流程、需求、业务规则 | `01｜产品文档` |
| 技术设计、架构、实现、部署 | `02｜开发文档` |
| 数据、接口、配置、字段映射 | `03｜数据、接口与配置` |
| 按环境记录实际部署的改动；正式服与测试服分篇维护 | `04｜更新日志` |
| 缺陷、故障、根因、修复 | `05｜问题记录` |
| 个案处理、临时绕行、人工补偿 | `06｜特殊情况记录` |
| 业务人员操作说明的关联入口 | `07｜操作手册关联` |
| 已废弃或被替代资料 | `90｜历史归档` |

## 系统简称、子项目与编号

系统简称、大小写、子项目及编号前缀以每次实时读取的《知识库文档编写与维护规则》登记表为准，不在本 Skill 或参考文件中复制一份静态映射。不得沿用旧文档、历史上下文或仓库名称中的旧简称作为默认值；登记值中的空格也应保留。

- 先确定主系统与子项目，再从登记表取得编号前缀；跨子项目文档使用主系统前缀，归属不明确时先读取正文与关联资料。
- 已有文档的标题、正文编号及关联引用应保持一致；新建文档先核对当前前缀下的现有编号，避免冲突。
- 用户明确要求迁移旧编号时，先保存标题、正文和节点标识的快照，建立旧编号到新编号的映射并检查重复；再原地修改标题、正文编号和关联引用，保留现有链接及节点。未授权迁移时，不批量重编号。
- 迁移只处理文档标识与登记简称，不把业务数据、证书编号、代码、仓库名或 URL 中的相似字符串当作文档编号。完成后按映射回读，并检查旧编号残留和新编号冲突。

## 判断文档类型

先判断用户请求是否是更新日志、问题记录或特殊情况记录。它们各自独立成篇，不能塞进 PRD 或技术设计中。

其余需求按以下规则处理：

1. 默认先形成“需求交付草案”。草案可同时含产品与技术信息，但不得成为正式规则的唯一来源。
2. 若只涉及文案、展示顺序、明确配置或既有能力的小范围调整，并且不改变数据、接口、关键链路或发布方式，可以创建一篇合一文档。正文内必须分开“业务规则”和“实施说明”。
3. 命中下表任意两项时，必须生成或更新一份 PRD 与一份技术设计，并在两篇文档中互链。

| 技术复杂度条件 |
|---|
| 数据表、字段映射或历史数据变化 |
| 接口、第三方服务或跨系统同步 |
| 审批、订单、支付、证书或合同等关键链路 |
| 权限、身份、token、敏感信息或安全 |
| 异步回调、重试、幂等、补偿或定时任务 |
| 灰度、迁移、发布、回滚或监控 |

只命中一项但存在明显技术风险、多人协作或长期维护成本时，也应拆分并说明原因。

## 产品文档写法

产品文档使用实时飞书《产品文档通用模板》的信息字段和内容边界，正文按实际功能组织，不把模板中的编写指引当作必填目录。

- 文档标题之后，第一个正文标题固定为“文档信息”，紧接二列信息表；字段按下文“写入与归档流程”和实时模板填写。摘要、提示块、背景和正文都放在信息表之后，不把文档信息移到文末或压成一句话。
- 文档标题和章节标题直接说明重点，使用“可选课程范围”“学期切换与历史记录保留”“验收标准与待办”等明确表述，不使用疑问句或“先看这次解决什么问题”之类引导句。
- 根据信息关系，按实际功能、用户任务、业务对象或操作流程安排正文。小调整可以只写改前/改后、必要示例和验收点；单功能围绕操作、规则及例外展开；复杂功能再按场景拆分。以上是选择依据，不是新的固定章节顺序。
- 背景、目标、范围、角色、流程、字段、权限、异常、验收和待确认项是按需覆盖的信息，不要求逐项独立成章。相邻内容可合并，不适用的章节直接省略；不为凑模板留下“无”“/”或空表，也不因精简而删掉真实限制、未决问题和验收条件。
- 信息表后先用简短业务语言说明功能重点。表格用于条件判断、对比和字段映射；操作用步骤，解释用短段落。确需术语时就地解释，复杂规则可用标明为示例的具体情形帮助理解，不编造业务数据或已上线结论。
- 修订时将已确认补充合并进对应功能段落，减少重复与相互矛盾的说法；历史修订保留在变更记录或来源链接。文档有效、测试服交付、正式上线和业务验收分别表达，不用文档状态代替发布状态。

## 编写边界

编写或修订更新日志时，先读取[更新日志写法与维护](references/release-notes-writing.md)及[项目更新文档登记](references/project-release-pages.md)。所有项目均按环境分开：每个项目分别持续维护“项目｜正式服更新日志”和“项目｜测试服更新日志”，不在同一篇内用章节混放。文档信息放最前，每个环境按自身实际部署日期倒序排列，每次更新的功能点从 1 开始编号，注意事项嵌套在对应功能下。根据项目和环境定位固定页面，不为每次发布重复建页。

测试服日志须细致说明适用端、入口与前置条件、操作顺序、业务判断及结果、异常与覆盖影响、已验证结果和待验收场景，按功能逻辑组织，不只罗列提交或复制正式服短公告。仅有实际测试部署依据的功能进入测试服更新时间线；未部署、状态不明的材料单列待发布/待核实，不能冒充线上能力。

测试部署、业务验收、正式发布是三个独立状态。测试服条目的“已上线”专指已正式发布：取得对应功能及端的正式发布依据后，写“已上线（正式服）”、实际正式发布日期和正式日志链接，保留原测试部署日期；仅测试部署或测试通过时写“未上线（正式服）”，证据不足写“正式发布待核实”，均不得标记已上线。部分端正式发布时逐项标注，不能将整个批次标为全部上线。正式发布后同时更新正式服日志和原测试条目；上线不等于验收通过，回滚或撤回须保留状态变更记录。详细发布证据放关联技术记录。

当前事项明确归属教师发展服务时，先读取[师资文档表达规则](references/teacher-documentation.md)，结合仓库规范组织产品正文、更新摘要和分项验收。该补充只适用于师资，不修改其他系统的文档口径。

产品文档是业务规则的唯一事实源，内容限定在以下适用信息中；这份清单不是固定章节模板：

- 背景、目标、范围与非范围。
- 角色、业务流程、页面与操作。
- 业务字段含义、必填规则、业务校验、状态与权限。
- 用户可见异常、验收标准、产品待确认项。

技术文档是实现方案的唯一事实源，只写：

- 改动范围、架构和调用链。
- 表/实体/字段、数据迁移、兼容、接口、配置与第三方集成。
- 前后端和任务实现范围、安全、审计、幂等、重试、补偿。
- 测试联调、发布、回滚、监控、研发待确认项。

保持两者一致但不重复定义事实：PRD 不写真实表名、接口参数、SQL、部署方案；技术文档不重新定义业务目标或验收。技术限制改变业务规则时，先回写 PRD 并提升版本。

真实 `token`、`secret`、账号密码、个人敏感信息不得写入正文、示例或日志。

## 版本与分支记录

项目发布版本、文档版本、Git 分支和 Git commit 是不同对象，必须分别记录，不能互相替代：

- 项目发布版本：适用时先从唯一版本源读取 SemVer 值，例如 `0.3.0`、`1.4.2-rc.1`；发布标签写为 `v1.4.2`。按2026-10-25用户对所有项目的统一授权，在已授权的开发/发布任务中自动维护版本源、CHANGELOG和标签，无需逐次确认版本号；实际部署、默认分支推送、数据及权限操作仍按各任务授权。
- 文档版本：只表示当前 PRD、技术设计或记录本身的修订，不等同软件版本。
- Git 分支与 commit：记录本次实现或发布所依据的真实分支名和短 commit；未核实时写 `[待确认]`，不得编造。

在 PRD 和技术设计的“文档信息”增加“项目版本 / 当前分支 / 发布标签（适用时）”。更新日志按每次发布保留实际日期、产品版本及来源；“上一版本 -> 本版本、变更级别、发布分支、发布 commit、关联 PRD/技术设计”等完整发布证据可放入关联技术或发布记录。项目时间线不把多次发布压成一个版本。只改文档或构建配置且未实际发布时，不虚增软件版本或发布次数。

项目时间线开头保留文档状态、维护人和复核日期；实际产品版本与上线日期写在各次更新中。分支、标签、提交、制品摘要及恢复步骤集中到关联技术或发布记录，保持完整追溯。

## 写入与归档流程

1. 读取现行治理规则、对应模板和目标系统现有栏目。
2. 检查同名或同事项的有效文档；已有有效文档优先更新，不重复创建。若要替代旧正式文档，先得到用户明确同意。
3. 按当前模板写入中文正文，开头用信息表列明名称、编号、文档修订、产品版本、状态、负责人、系统/子项目/具体端和最后复核；适用的分支、标签及关联资料按模板记录。产品文档的信息表置于首个“文档信息”标题下，正文依上文“产品文档写法”按功能组织。负责人取已验证的当前CLI登录用户，不用未知占位；其他无法核实的事实明确待确认，不能编造。
4. 用 `wiki +node-create --as user` 在目标栏目下创建节点，或对确认的既有文档做最小范围更新；再用 `docs +update --as user` 写入内容。创建节点后的真实 doc token 以命令返回为准。
5. PRD 与技术设计互相写入飞书链接。草案若保留，标为“草稿”或“已被正式文档替代”，并链接正式文档。
6. 上线后，按以下规则更新项目时间线或维护专项记录：
   - 更新日志：按“项目＋环境”登记定位固定页面，在该环境实际部署日期位置增加或修订条目；同一次发布合并维护，不重复插入。每次更新的功能从 1 编号，注意事项归于对应功能。测试服部署先写测试日志；正式发布后写正式日志并回写原测试条目的正式状态、日期与链接，不覆盖原测试日期。独立发布证据继续使用 `系统-REL-年份-序号`；固定汇总页本身不冒充一次新发布。迁移既有混合页时先快照，目标测试页写入并回读后，再定向移除正式页内相应测试/待核实内容，保留来源与历史链接；不把未发布记录改写为已上线。
   - 问题记录：`系统-ISS-年份-序号`，写现象、影响、根因、修复、验证与后续动作。
   - 特殊情况记录：`系统-EXC-年份-序号`，写正常规则、例外原因、审批、处理、时效和恢复条件。
7. 以 `docs +fetch` 回读每篇刚写入的文档，并以 `wiki +node-get` 或 `wiki +node-list` 验证父级栏目。检查标题、状态、适用的关键事实与验收、互链和归档位置；产品文档还须检查文档信息位于最前、标题直述重点、正文按实际功能组织，不以固定章节名称或数量作为完成标准。更新时间线还须核对项目及环境绑定、日期顺序、功能编号、注意事项所属功能、重复条目及来源；测试条目的“已上线”必须能回链正式发布证据，且待验收状态未被覆盖。

## 输出要求

完成后用中文简要说明：处理的系统和事项、创建或更新了哪些文档、合一或拆分的判断、每篇文档的飞书链接、以及尚未确认但影响交付的事项。

没有完成回读验证时，明确说明未完成，不能声称已归档。
