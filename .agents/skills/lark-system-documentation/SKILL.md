# 系统文档归档

将一次需求、改动或异常沉淀到飞书知识库中正确的系统和栏目。完成标准是“文档已按现行规则归档并回读验证”，不是只生成一段正文。

## 先读的规则

1. 先阅读 [知识库配置](references/knowledge-base.md)，确认目标空间和治理文档链接。
2. 按当前环境的 `lark-doc`、`lark-wiki`、`lark-shared` Skill 执行。文档内容读写必须显式使用实际身份参数 `--as user` 或 `--as bot`，并按本 Skill 的“负责人判定”规则写入负责人。
3. 每次任务先从知识库读取有效的《知识库文档编写与维护规则》、产品模板、技术模板；它们是唯一的当前标准。本 Skill 不复制或覆盖这些标准。
4. 写入、创建、移动前确认用户的任务已授权这些写操作。删除、覆盖既有正式文档、移动历史资料或改变权限时必须单独取得明确授权。

## 任务输入与定位

先从用户材料中提取：系统、功能或事项、目标读者、文档类型、当前状态、负责人、版本、关联资料和是否已经上线。

若关键信息未提供：

- 系统不明确时，先在目标 Wiki 的一级目录中检索，无法可靠归属才询问。
- 负责人不再从用户材料猜测或固定写 `[待确认]`：先按“负责人判定”读取本次 CLI 写入所用身份；只有身份名称无法解析时才写 `[待确认]`。
- 版本、发布日期等非阻塞字段仍可写 `[待确认]`，不可自行编造。
- 有已有草案、旧文档或链接时，先读原文和对应系统目录，避免重复创建。

## 负责人判定

文档“文档信息”中的负责人必须是本次实际执行 `wiki` / `docs` 写操作的 CLI 身份，不要把负责人留空，也不要写成用户口述的其他人。

1. 写入前执行 `lark-cli auth status --json --verify`，只读取身份名称，不输出 token、secret 或完整 scope。
2. 根据写入命令的 `--as` 选择对应身份：
   - `--as user`：使用 `identities.user.userName`；
   - `--as bot`：使用 `identities.bot.appName`。
3. 如果命令使用了 `--as` 以外的自动身份，先用 `lark-cli whoami` 确认实际生效身份，再回到上述映射；不得凭经验猜测。
4. 写入后回读文档，确认“负责人”与实际写入身份一致。身份不可用、未验证或名称字段为空时，才写 `[待确认]`，并在交付说明中指出原因。

将文档归入下列标准栏目；实际 node token 必须每次从 Wiki 实时查询，不能只依赖本地记忆：

| 文档类型 | 标准栏目 |
|---|---|
| 系统定义、边界、关键入口 | `00｜系统总览` |
| 正式 PRD、业务流程、需求、业务规则 | `01｜产品文档` |
| 技术设计、架构、实现、部署 | `02｜开发文档` |
| 数据、接口、配置、字段映射 | `03｜数据、接口与配置` |
| 已上线改动 | `04｜更新日志` |
| 缺陷、故障、根因、修复 | `05｜问题记录` |
| 个案处理、临时绕行、人工补偿 | `06｜特殊情况记录` |
| 业务人员操作说明的关联入口 | `07｜操作手册关联` |
| 已废弃或被替代资料 | `90｜历史归档` |

## 判断文档类型

先判断用户请求是否是更新日志、问题记录或特殊情况记录。它们各自独立成篇，不能塞进 PRD 或技术设计中。

其余需求按以下规则处理：

1. 默认先形成“需求交付草案”。草案可同时含产品与技术信息，但不得成为正式规则的唯一来源。
2. 若只涉及文案、展示顺序、明确配置或既有能力的小范围调整，并且不改变数据、接口、关键链路或发布方式，可以创建一篇合一文档。正文内必须分开“业务规则”和“实施说明”。
3. 命中下表任意两项时，必须生成或更新一份 PRD 与一份技术设计，并在两篇文档中互链。

| 技术复杂度条件 |
|---|
| 数据表、字段映射或历史数据变化 |
| 接口、第三方服务或跨系统同步 |
| 审批、订单、支付、证书或合同等关键链路 |
| 权限、身份、token、敏感信息或安全 |
| 异步回调、重试、幂等、补偿或定时任务 |
| 灰度、迁移、发布、回滚或监控 |

只命中一项但存在明显技术风险、多人协作或长期维护成本时，也应拆分并说明原因。

## 编写边界

产品文档是业务规则的唯一事实源，只写：

- 背景、目标、范围与非范围。
- 角色、业务流程、页面与操作。
- 业务字段含义、必填规则、业务校验、状态与权限。
- 用户可见异常、验收标准、产品待确认项。

技术文档是实现方案的唯一事实源，只写：

- 改动范围、架构和调用链。
- 表/实体/字段、数据迁移、兼容、接口、配置与第三方集成。
- 前后端和任务实现范围、安全、审计、幂等、重试、补偿。
- 测试联调、发布、回滚、监控、研发待确认项。

保持两者一致但不重复定义事实：PRD 不写真实表名、接口参数、SQL、部署方案；技术文档不重新定义业务目标或验收。技术限制改变业务规则时，先回写 PRD 并提升版本。

真实 `token`、`secret`、账号密码、个人敏感信息不得写入正文、示例或日志。

## 写入与归档流程

1. 读取现行治理规则、对应模板和目标系统现有栏目。
2. 检查同名或同事项的有效文档；已有有效文档优先更新，不重复创建。若要替代旧正式文档，先得到用户明确同意。
3. 按当前模板写入中文正文。首段或“文档信息”必须包含名称、编号与版本、状态、负责人、涉及系统、关联文档、最后复核日期；负责人按“负责人判定”写入实际 CLI 身份，只有解析失败时才写 `[待确认]`。
4. 用已解析身份执行 `wiki +node-create --as <identity>` 在目标栏目下创建节点，或对确认的既有文档做最小范围更新；再用 `docs +update --as <identity>` 写入内容。创建节点后的真实 doc token 以命令返回为准。
5. PRD 与技术设计互相写入飞书链接。草案若保留，标为“草稿”或“已被正式文档替代”，并链接正式文档。
6. 上线后，按以下规则创建独立记录：
   - 更新日志：`系统-REL-年份-序号`，链接对应 PRD、技术设计和发布版本。
   - 问题记录：`系统-ISS-年份-序号`，写现象、影响、根因、修复、验证与后续动作。
   - 特殊情况记录：`系统-EXC-年份-序号`，写正常规则、例外原因、审批、处理、时效和恢复条件。
7. 以 `docs +fetch` 回读每篇刚写入的文档，并以 `wiki +node-get` 或 `wiki +node-list` 验证父级栏目。检查标题、状态、模板关键章节、互链和归档位置。

## 输出要求

完成后用中文简要说明：处理的系统和事项、创建或更新了哪些文档、合一或拆分的判断、每篇文档的飞书链接、以及尚未确认但影响交付的事项。

没有完成回读验证时，明确说明未完成，不能声称已归档。
